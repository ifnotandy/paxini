# 标定：两类，一件已实现、一件没写

"标定"在这个仓库里指两件完全不相干的事，先把它们分开，免得混着谈：

| | 手套零点标定 | 相机标定 |
|---|---|---|
| 解决什么 | 把手套的读数归零 | 把像素和空间连起来 |
| 改在哪 | 手套内部存储，设备端持久化 | 主机侧一份 `calib_*.json` |
| 谁在用 | 采集端直接受益（角度、合力都归零） | 只有派生阶段用（指尖三维、深度） |
| 现状 | **已实现**，真机还没跑过（清单 B9） | **没实现**，设计见本文 §2 |
| 代码 | `Cap_Quest/calib/hand_calib.py` | 待建 `calibrate.py` |
| 依赖 | 只要 SDK | 要 OpenCV、标定板、（G3 起）指节模型 |

两者没有共用的量、没有共用的代码路径。下面 §1 讲手套，§2 讲相机。

---

# 1. 手套零点标定（已实现）

工具：`Cap_Quest/calib/hand_calib.py`，只依赖 SDK，不依赖 numpy / h5py / opencv。

## 1.1 SDK 的"标定"到底改了什么

PxCap3 SDK 只有两个写接口，都是**把当前状态写成零点，存进手套自己的存储**：

| 接口 | 作用 | 生效范围 |
|---|---|---|
| `set_encoder_calibration()` | 4 路磁编码器标零 | 之后 `get_encoder_raw_data()` 的展开编码值以新零点为 0，角度随之平移 |
| `set_sensor_calibration()` | 10 路传感器标零 | 之后 `get_sensor_resultant_force()` 的合力以当前受力为 0 |

由此有三条必须记住的推论：

- **不是主机侧后处理。** 偏移量不在数据里、不在程序里，而在设备里。换电脑、换采集
  程序，零点照样有效；`data.h5` 里的 `joint_angles_deg` 已经是标零后的值，读出来就是。
- **改了不可逆。** 没有"撤销"，标错了只能重标。所以要标之前先看闸门。
- **只管零点，不管方向、不管量程、不管坐标轴。** §2.1 里"力矢量的坐标系没写"那条问题，
  标零解决不了。

`PxCap3` 没有 `get_*_calibration` 这类回读接口（那是 PxCapUltra 才有的），所以"当前
零点是什么"没法直接问设备，只能看读数：**编码器角度接近 0、空载合力接近 0，就是标过的**。

## 1.2 什么时候该跑

| 现象 | 跑哪个 |
|---|---|
| 摘下手套、空载时 10 路合力明显不为 0（漂了） | `sensor` |
| 换了握姿基准，或要一段"从零开始"的关节角 | `encoder` |
| 某路角度读数跳变、卡死 | 先 `magnet` 看磁编码器，再决定要不要标 |
| 拿到新手套 / 换过传感器模组 | 三个都跑一遍 |

**采集进行中不能跑**：SDK 明确要求标定期间停止轮询与连续采集，否则返回错误码
4000 那一类。`hand_calib.py` 自己不启动采集，但跑之前要确认 `collect_cap.py` 已经停了。

## 1.3 命令

```bash
cd Cap_Quest

python3.10 calib/hand_calib.py info                    # 只读：SN、固件、故障、4 路角度、10 路合力
python3.10 calib/hand_calib.py ports                   # 串口列表，标出 USB 28e9:018a 那一个
python3.10 calib/hand_calib.py encoder --dry-run       # 只跑静止检查，不写设备
python3.10 calib/hand_calib.py encoder                 # 磁编码器标零（要交互输入 yes）
python3.10 calib/hand_calib.py sensor                  # 传感器标零
python3.10 calib/hand_calib.py magnet                  # 静态磁检测，4 路逐项出状态
python3.10 calib/hand_calib.py selftest                # 离线自检 7 项，不连设备
```

公共参数：`--hand-port auto|/dev/ttyACM0`、`--yes`（免交互）、`--dry-run`、`--samples`、
`--interval-ms`、`--settle-s`、`--report/--no-report`。这几个写在子命令前后都认。

## 1.4 两个闸门

标零的唯一前提是"这一刻的状态就是你要的零点"，所以程序在写设备前先采样再看：

**编码器**：采样窗内 4 路角度的**峰峰值**超过 `--max-jitter-deg`（默认 0.3°）就拒绝。
角度绝对值不重要——标零本来就是要把它清零。

**传感器**：分两档，因为绝对值单独没有意义（旧零点漂移会让空载也读 0.7 N）：

| 判据 | 默认 | 含义 |
|---|---|---|
| 窗口内摆动峰峰值 | ≤ 8 (0.8 N) | 有人在按压或揉动 |
| 窗口内均值偏置 | ≤ 20 (2.0 N) | 明显有负载 |
| 摆动合格但偏置 > 8 | — | 只警告，提示"更像零点漂移，建议标零" |

被拦住时程序不写设备、退出码非 0；`--force` 可强行继续，但报告里记 `forced: true`。
**不要养成加 `--force` 的习惯**：带载标零等于把外力定义成零，之后所有力都偏一个常值，
而且没有痕迹可查。

## 1.5 判据与留证

标零后自动复读验证：

| 项 | 判据 |
|---|---|
| 编码器零点残差 | 4 路 `|deg|` ≤ `--max-residual-deg`（默认 2.0°） |
| 传感器空载残差 | 10 路单轴 `|均值|` ≤ `--max-residual-raw`（默认 5 = 0.5 N） |

超判据时退出码 1，并提示下一步该查什么（手在动 / 磁铁位置 / 传感器故障项）。

每次运行默认写一份报告到 `Cap_Quest/calib/hand/hand_<SN>_<时间>.json`，内容是标定前后的
原始读数、闸门结果、判据与结论。**报告不入库**（`.gitignore` 里有 `**/calib/hand/`），
只在本机留证：它记录的是"这台设备在什么时候被改成了什么零点"，重标一次就多一份，
以后回溯"这条数据用的是哪次标零"时去采集机上看。

## 1.6 坑

- **必须 `python3.10`**：系统里 3.12 的 `import pxhandsdk` 能过，但类不存在。
- **`--dry-run` 也会采样**，手要保持和真要标定时一样的姿态，否则检查结果不代表实际。
- **串口独占**：`collect_cap.py`、`hand_calib.py`、厂商上位机不能同时开同一个口。
- **静态磁检测期间手要静止**，检测结果是"磁场是否正常"，动了会误判成异常（状态 1）。
- 报告里的 `note` 字段写死了这句：标定写在设备端，报告不是主机侧偏移量。

# 2. 相机标定（空间几何，未实现）

**这个功能在仓库里不存在——不是"没验证"，是"没写"。** 2026-11-13 复查：
`Cap_Quest/` 下的 `*.py`、`*.json`、`*.sh` 里 grep `calib|标定|intrinsic|extrinsic|内参|外参|distort`
**零命中**（`hand_calib.py` 是手套零点，与像素无关）；`data.h5` 的 `meta/` 组（见
[`HDF5结构说明.md`](HDF5结构说明.md) §6）只记录采集参数、版本和自检结果，没有任何
标定信息的出处；`requirements.txt` 里也没有 OpenCV——采集端**从不碰像素**，只把 mkv 原样存下来。

采集端目前唯一的承诺是：**每个来源都带自己的时间戳，三条时间轴可以互相换算**。
但时间对上了不等于坐标对上了——手套的角度活在关节空间，相机的像素活在图像平面，
Quest 的位姿活在 tracking-origin，把三者放进同一个世界的那些变换，只能靠标定。

## 2.1 现在答不了的问题

| 问题 | 能不能答 | 卡在哪 |
|---|---|---|
| 某帧指尖在空间里的三维位置 | **不能** | 只有 4 路关节角（`joint_angles_deg`），没有指节长度，也没有正运动学 |
| 10 路合力的分量在哪个坐标系 | **不能** | `resultant_force` 只写了单位 0.1 N 和符号规则，**没写坐标系** |
| 相机画面里的点 ↔ 哪个槽位 | **不能** | 要相机内参 + 手套→相机外参 |
| 视频里那只手离镜头多远 | **不能** | 单目 + 无内参，只能给"在图像里的位置" |
| Quest 轨迹能不能叠到手套上 | **不能** | 两边没有变换；且 C8（`sdk_timestamp_ns` 时钟域）还没解决 |
| 两条数据在时间上怎么对应 | **能** | 见 [`时间戳说明.md`](时间戳说明.md) |

一句话：**时间已经通了，空间一寸没通。**

所以现在这个仓库能支撑的都是"随时间变化的东西"——点数值、合力模长、关节角曲线、
视频里看得见的手指动作。任何带"几厘米、几度、在哪"的判断都还没有依据。

## 2.2 要标的四组量

**验收判据统一登记在 [`待验证清单.md`](待验证清单.md) G 组，这里只写做法。**

### G1 相机内参 + 畸变（每路一套）

- **输入**：标定板（棋盘格或 ChArUco）静态摆 15~25 个位姿，位姿要覆盖画面四角与中心，
  至少 3 个倾斜很大的视角
- **产出**：`fx fy cx cy`、`k1 k2 p1 p2 k3`；两路相机各自的 720p 参数**不能混用**
  （换了分辨率必须重标，内参不随分辨率线性缩放）

### G2 双相机外参（cam1 → cam0）

- **输入**：同一块板同时出现在两路画面里，拍 20 组以上，覆盖重叠区
- **产出**：`R`（3×3）、`t`（3×1，米）、基线长度

### G3 手套 → 相机（hand frame → cam0）

这是最麻烦的一组，因为**手套没有三维输出**：SDK 给的是 4 路磁编码器角度
（`encoder_raw` / `joint_angles_deg`），要变成三维点还缺一级——指节长度与运动学链。
两种做法：

1. **有产品模型时**：用厂商给的指节长度与关节链做正运动学，再用标定板标
   `hand → cam0` 的刚体变换
2. **没有模型时**：退一步只标"槽位在画面上的位置"——把 10 个槽位当成 10 个贴片标记，
   用一个平面靶把这 10 个点在 cam0 下的三维位置一次性标出来（前提是手保持固定姿态），
   这样只能得到**某一姿态下**的槽位坐标，姿态一变就失效

建议先按 1 做，2 只作为临时可视化手段（画"力作用在画面哪里"够用，不能算距离）。
**在 G3 之前，任何"指尖三维位置"的结论都不成立**，包括用双相机三角化出来的。

### G4 Quest tracking-origin → 相机 / 手套

- 前置条件是 C 组：C3~C8，尤其 **C8**（`sdk_timestamp_ns` 属于哪个时钟域）。
  时钟域没定，就算空间标好了也只能对齐个大概
- 产出：`T_quest_to_cam0`（4×4），把 `pose_6d` 搬进相机坐标

## 2.3 必须先定下来的约定（现在文档里是空的）

标定之前得先把这几件事写死，否则标出来的数没法解释：

| 项 | 现在 | 要定成什么 |
|---|---|---|
| 手套坐标原点 | 未定义 | 掌心几何中心 or 腕部法兰？轴指向？（建议 +X 指向指尖、+Z 出掌面） |
| 力矢量的坐标系 | 文档只写了单位与符号 | `resultant_force` 的 xyz 是手套本体坐标、还是指节切/法向？需厂商确认或按 G3 的旋转推 |
| 相机坐标约定 | 未定义 | OpenCV（+Z 朝前、+Y 朝下）还是 ROS（+Z 朝前、+Y 朝上）？定一个写进文档 |
| 单位 | 相机/Quest 是米 | 手套侧若厂商给毫米，派生数据统一转米 |
| `cap_side` / `pose_side` | `right` | 标定文件要带同样的 side，左右不能混用 |

`data.h5` 只加两条 `meta/` 属性：`calib_id` 与 `calib_sha256`（指向这份文件），
**不把矩阵写进每次采集**——否则同一套标定在几百个文件里各存一份，重标一次要全改，
而且没法回答"这条数据到底用的哪套标定"。

**版本影响**：`meta/` 加属性不改变 `cap/`、`quest/` 的行轴与形状，按
[`../README.md`](../README.md) §0.1 第 7 条**不必升 `format_version`**；
但要在 [`HDF5结构说明.md`](HDF5结构说明.md) §6 的属性表里加两行（那是定点改，一行一条）。

## 2.5 采集端要加的东西

| 新增 | 做什么 | 不改什么 |
|---|---|---|
| `calib_capture.py` | 复用 `camera_ffmpeg.py` 的双路录制，只存 mkv（或按 1 fps 存 PNG），不建 HDF5 行轴 | 不碰 `collect_cap.py` 的采集逻辑 |
| `calibrate.py` | 读 `captures/` → `cv2.calibrateCamera` / `stereoCalibrate` → 写 `calib_*.json` | — |
| `derived/` 脚本 | 给 `data.h5` + `calib.json`，另存 `derived/*.h5`（指尖轨迹、相机坐标下的力） | **不改原 `data.h5`**，派生结果单独一个文件 |
| `collect_cap.py --calib` | 只把 `calib_id` / sha256 写进 `meta/`，其余一行不改 | 采集主循环、行轴、时间戳全部不动 |
| `requirements.txt` | 加 `opencv-python`（只在标定与派生阶段用） | 采集主流程的依赖保持最薄：numpy / h5py / matplotlib / xrobotoolkit |

刻意**不往采集端加相机标定参数校验**：采集时不看像素，加进去只会让"采得到"变成
"采不到"。标定缺了就在派生阶段报错。

## 2.6 分三步走

1. **阶段一（不依赖手套，也不依赖 Quest）**：G1 + G2。做完就有了"某个像素对应空间一条射线"，
   双相机能三角化出三维点、能测深度。这一步只用到 mkv 和标定板，随时可做。
2. **阶段二**：G3。要拿到指节长度/运动学链，才能把 10 个槽位变成三维位置。
   拿不到就退到"某姿态下的槽位贴片坐标"，别拿它算距离。
3. **阶段三**：G4。等 Quest 到位、C8 解决之后再动；在那之前 `Paxini-Align/` 做跨源
   时间配对有意义，做空间融合没有。

状态与判据登记在 [`待验证清单.md`](待验证清单.md) 的 **G 组**，做完一条把结论写进那一行；
§2.1 那张"答不了的问题"表同时就是"现在能做什么/不能做什么"的边界。
